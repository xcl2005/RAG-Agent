# 设计说明

完整、与当前代码逐项对应的设计已经迁移到 [architecture.md](architecture.md)。

阅读时重点关注四条主线：

1. LangGraph 不是线性包装，而是具有“回答 / 有界重试 / 拒答”和“一次引用修复”的条件图。
2. Dense、FTS5、加权 RRF 与 reranker 的分数含义不同，因此保留原始信号并分别校准门槛。
3. SQLite 是文档原文和 manifest 的权威来源；Qdrant 命中必须回表解析，孤儿向量不会进入上下文。
4. 当前 checkpoint 提供持久化多轮状态和故障恢复基础，但尚未实现人工中断后的用户侧恢复控制台。

技术是否“更新”的判断、MCP/A2A/GraphRAG 取舍见
[technology-radar-2026.md](technology-radar-2026.md)。

## Web 工作台

界面采用“轻量文档工作台”而不是卡片式后台模板：

- 桌面为 `296px / 自适应正文 / 376px` 三栏；窄于 `1320px` 时运行面板变为抽屉，
  窄于 `760px` 时资料库也变为抽屉。
- 正文、侧栏、辅助信息分别使用约 `15px / 13px / 11px` 的字号阶梯；不再用
  8–10px 承载文件名或运行状态。
- 空会话使用无阴影的文档式欢迎区；首次提问后自动隐藏，回答以连续文档流呈现。
- 阴影只用于输入框、抽屉和确认弹窗；列表与证据依靠留白、细分隔线和单一电蓝组织。
- 来源行展示持久化 `display_name`，绝对路径和上传哈希只留在服务端。删除按钮使用独立
  站内确认弹窗、逐行忙碌状态和事件委托，移动端触控区域不小于 `44px`。

## 来源生命周期

上传时同时保存两种身份：

1. `source`：服务端稳定存储路径，用于幂等文档 ID 和同名修订。
2. `display_name`：用户上传的原始 basename，只用于 UI、Prompt 与引用标题。

旧数据库启动迁移时会移除 12 位存储哈希；若清洗过程只把空格变为下划线，会用已有
文件名哈希校验并精确恢复空格组合。无法唯一恢复时保守使用清洗后的 basename。

删除只对浏览器上传的受管文件开放。持有入库锁后，SQLite 会在一个事务中删除 manifest、
chunks 和 FTS；随后按 `document_id` 清理 Qdrant 孤儿向量，并且只在来源仍位于受管
`uploads` 目录时 unlink 文件。服务器路径导入的原文件不会被 Web API 删除。
