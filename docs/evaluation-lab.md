# 我如何证明一次检索修改有用

这个实验室适合第一次把 RAG 项目讲清楚：运行一条命令，就能从虚构资料建立临时索引，看到原问题检索和术语扩展检索的真实差异。先理解这条短链路，再研究模型和 Agent。

已执行的一次测量与正反案例见 [实验记录](experiment-notes-2026-09.md)，请复跑核对，不把记录当成自己的已完成经历。

## 运行

在已经安装项目依赖的环境中，从仓库根目录执行：

```powershell
.venv\Scripts\python.exe scripts/eval_portfolio.py
```

其他系统或已经激活虚拟环境时：

```bash
python scripts/eval_portfolio.py --profile sparse
```

不需要 API Key、Docker、模型下载或网络。它不读取应用的 `.env`，不使用上传资料，也不打开现有 SQLite/Qdrant 数据库。每次建立独立临时 SQLite，运行结束自动关闭和清理。报告保存在被 Git 忽略的 `reports/portfolio/`，采用时间戳命名，保留历次结果。

当前只有 `sparse` 配置；没有实现或宣称测过 `hybrid`。后续若增加向量实验，应使用独立临时集合、固定 embedding 模型版本，并单独报告模型加载时间与查询时间。

## 代码和数据

主要实现是 `src/rag_agent/evaluation/lab.py`，入口是 `scripts/eval_portfolio.py`。语料位于 `data/eval/portfolio/corpus/`：8 份虚构工程团队短文档，覆盖发布、API、入库、检索、安全、观测、评测和故障演练。

`cases.json` 包含 32 个问题：20 个可回答问题（其中 5 个需要跨文档），以及 12 个不可回答问题（4 个主题外问题、8 个与资料用词接近但缺少答案的难负例）。可回答题标注相关来源和原文证据；负例写明为什么没有答案。加载时会验证证据原文确实存在。

这是随实现共同编写的开发集，术语表也已见过这个领域，不能称为独立测试集。数据完全虚构，不是你的实习经历、公司制度或生产事故。

## 这次到底比较什么

两组都调用项目真实的字符分块器、SQLite FTS5 搜索和 RRF 融合。默认每块 300 字符、重叠 40 字符、每次召回最多 20 块，最后按来源去重并返回前 5 个来源。分块参数是实验参数，与虚构文档里描述的团队规则无关。

baseline 只检索用户原问题。expanded 保留原问题，再按固定双语术语表追加最多两个变体。例如 `backoff` 可以触发“重试 指数退避 随机抖动”，`chunk overlap` 可以触发“分块 重叠”。原问题权重为 1，扩展权重为 0.7。两组没有调用语言模型、没有重排器，也没有生成任何答案。

检索只收到问题文本。相关来源和原文标注仅用于事后计算指标，不会作为查询提示。规则、阈值和参数全部进入 JSON 报告，方便核对。

## 怎么读结果

| 指标 | 能说明什么 | 不能说明什么 |
|---|---|---|
| Recall@5 | 标注的相关来源有多少进入前五 | 找到的片段已经足够回答全部细节 |
| MRR | 第一个相关来源是否排得靠前 | 跨文档题所需来源都已找到 |
| nDCG@5 | 相关来源在前五中的排序质量 | 模型生成答案准确 |
| all_relevant_retrieved_rate | 可回答题是否找齐标注来源 | 找齐来源就一定找齐了原文证据 |
| false_refusal_rate | 可回答题有多少被门控拦下 | 线上拒答率或模型能力 |
| false_answer_rate | 不可回答题有多少被门控错误放行 | 模型真的已经生成了错误答案 |
| 查询 p50 / p95 | 本次本机检索流水线的耗时分位数 | API 全链路延迟或高并发吞吐量 |

排序指标只对 20 个可回答问题计算。负例没有“相关来源”，不能把它们当作排序得分为零混进均值。来源先去重、再截取 K，同时保留不相关来源在排名中的位置。

这里的门控是透明的实验基线：所返回来源的候选块中，只要有一个块的最高关键词覆盖度达到 `0.45` 就放行。覆盖度按各查询变体分别计算后取最大值，RRF 分数不参与门控。这不是运行中 Agent 的完整多信号门控，也不是可靠的语义充分性判断。

因此可能出现“Recall@5 很高，但误拒答仍高”：已经找到了正确来源，自然语言问题里没在文档出现的词却拉低了覆盖度。还可能出现“扩展降低误拒答，同时增加错误放行”：宽泛的变体匹配到了主题相关文字，却没找到问题要求的事实。这些失败本身就是实验要保留的结论。

逐题 JSON 会给出问题、查询变体、候选分块 ID、相关来源、返回来源、覆盖度和门控判断。`by_tag` 会分别统计术语、跨来源、难负例等类别。检查失败案例比只背总体分数更有用。

报告附带数据集 SHA256、Git 提交号和 dirty 状态、Python/SQLite 版本以及参数。dirty 为真表示工作区还有未提交代码，不能只拿提交号声称精确复现。精确字节发生变化时数据集摘要会变化；换机器目录不会改变摘要。

延迟采用一轮成对测量，两组执行顺序逐题交替，分位数采用 nearest-rank。初始化和建库耗时单列；写报告不计入查询时间。小语料上的单次毫秒结果容易受系统缓存影响，不能拿它宣称生产性能。

## 亲手完成三个实验

1. 先运行默认命令，在 JSON 里挑一个误拒答和一个错误放行。打开对应文档，用自己的话解释“找到了什么”和“还缺什么”。
2. 只改阈值，保持其他参数不动：

   ```powershell
   .venv\Scripts\python.exe scripts/eval_portfolio.py --sparse-threshold 0.25
   ```

   对比两次报告：排名应相同，门控决定可能变化。记录误拒答下降多少、错误放行增加多少。不能只报告其中变好的数字。
3. 自己新增 5 个问题，包括一个用词非常接近但答案缺失的负例。先写标注和理由，再运行。不要因为模型或检索失败而把负例偷偷改成正例。

完成后再建立未用于写规则或调阈值的独立测试集。第一版可以另请同学出题，你在冻结规则之后才查看测试结果。
