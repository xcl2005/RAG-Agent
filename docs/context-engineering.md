# 上下文工程：把检索结果变成模型真正看到的证据

源码入口：`src/rag_agent/agent/prompts.py` 与 `graph.py::prepare_context`。

## 问题不只是“检索多一点”

检索返回的是候选列表；模型实际收到的是一个有大小限制的字符串。二者不相等。
例如前三名都来自同一份申请文档，第四名才是另一个项目；不经选择地拼接会挤掉不同来源。
又例如 quote 取自完整 chunk，但模型只收到其前 150 字，界面便可能展示模型没看见的内容。

本轮修复了两个可复现的旧问题：

1. 多块之间的 `\n\n` 没被算进预算，实际字符串可能超限。
2. 首块截断后仍返回原始完整候选，quote 可能越过实际送入模型的文本。

另外，跳过放不下的大块后继续考察较小块，不再因为中间一块过长就终止整个遍历。

## 处理顺序

```text
通过相关性门控的候选
  → 首个通过单候选门控的证据放最前（预算锚点）
  → 同来源、仅空白不同的重复文本去重
  → 清单/比较问题：按来源轮流取块；事实问题：保持排序
  → HTML 转义 + 来源标签 + 分隔符全部计入预算
  → 保存实际可见文本的候选副本
  → 生成回答与校验 [S1…Sn]
```

### 为什么去重很保守

只合并同一个 `document_id` / `source` 且章节、页码、文档单元相同，规范空白后完全相同的文本。
不同来源的相同句子保留出处；`30 秒` 与 `60 秒`、`可以` 与 `不可以` 不合并。
同一文档 Production 和 Staging 章节的相同句子也保留，因为语义范围不同。
不使用模糊字符串阈值，因为数字和否定词只差一点却会改变事实。

### 为什么只对部分问题做来源多样化

包含“哪些、列出、汇总、比较”等字样的清单问题，使用简单可审计的规则触发。
先交错不同文档，再处理同一文档的下一块；为至多四个尚未处理的来源预留空间。
如果公平分配使唯一强证据的元数据也放不下，会退回强证据独占预算，trace 记录 `anchor_only`；
仍不能容纳则返回上下文构建失败，不让弱证据替代唯一强证据。
这不是学会了查询意图的分类模型，也不保证覆盖所有应答来源；英文/中文规则可能误判。
单份文档中的精确问题保留原排序，避免强行多样化引入噪声。

### 为什么使用字符预算

`MAX_CONTEXT_CHARS` 约束的是 evidence 字符串，包含转义膨胀、标签、属性与分隔符。
二分寻找能放入预算的原文前缀，再转义，避免切坏 `&lt;` 等实体。标签始终闭合。
它不包括系统提示词、问题、历史，也不是 token 预算。不同模型 tokenizer 不同；整个请求的 token 上限需要独立方案。

### 为什么候选要复制

`dataclasses.replace` 创建保留 chunk ID/分数/来源的新对象，只把 `text` 换成实际可见部分。
不修改检索结果或 checkpoint 中的原始候选。`source_list` 用副本生成 quote 和连续 `[S1…Sn]`，
因此被跳过的块不会留下编号空洞，quote 不会含被预算裁掉的原文。

## 怎样验证

项目根目录运行（PyCharm Terminal 同样可用）：

```powershell
.\.venv\Scripts\python -m pytest tests/test_prompts.py tests/test_agent_graph.py -q
```

重点用例：

- `test_exact_escaped_budget_including_separators`：多种大小、两种策略，`len(text) <= budget`。
- `test_context_keeps_part_of_top_result_when_budget_is_small`：quote 来自可见前缀，原候选不变。
- `test_context_skips_large_middle_hit_without_losing_later_evidence`：跳过大块仍保留后续证据。
- `test_dedup_preserves_conflicts_and_independent_provenance`：不吞掉冲突数字、否定词和独立来源。
- `test_overview_reserves_budget_for_multiple_long_documents`：长文档也有跨来源覆盖机会。

网页右侧“运行”新增“整理证据上下文”，显示实际片段数、文档数、去重数、字符用量和是否裁剪。
这些只用于解释选材过程，不是答案准确率。

## 已知边界与下一步实验

- 取前缀可能截掉块尾的关键句。后续可比较 query-aware 句窗与当前前缀策略，并评测证据覆盖。
- 门控针对原始块的检索信号，截断后并未重新验证语义充分性；不能由“过门控”推出“答案受支持”。
- 跨来源策略不保证回答完整；单来源重复去重也不能消除大量近似但不同的申请文书。
- 转义和风险标记不等于免疫 prompt injection。模型仍应把 evidence 当数据，而非指令。
- 当前引用校验是编号合同，不是逐句语义支持检查。

动手题：先写一个“相关句在块尾”的失败测试，再提出如何在固定预算里保留它。记录测试结果和取舍，
不要只把预算扩大十倍。这是一个你可以真正完成、能在面试中讲清的后续改进。
